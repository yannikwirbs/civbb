# 0078: Phase 0's gate is not yet passed; its evidence comes before Phase 1

Status: accepted
Date: 2026-11-24

## Context

ADR 0004 sets Phase 0's gate: "compiled avatars visually identical and clearly cheaper than baselines", and design
doc §21 says how it is measured: FLIP within threshold in every state, and less CPU per avatar than the same
avatar in Unity with an Avatars 3.0 emulator, with and without AvatarOptimizer or d4rk's optimiser. When M0.10
closed (2026-11-23), STATUS.md declared Phase 0 done and the next session was told to split the Phase 1 epic #39,
whose own text says to split it "when Phase 0 passes its gate".

The Phase 0 health check (`docs/ai/reviews/phase-0-health-check.md`) found:

- *Behaves the same*: proven. Animator, muscle, body pose, constraint, contact and PhysBone behaviour replays
  Unity's and the VRChat SDK's recordings in CI.
- *The compiler keeps the look*: proven against our own import (FLIP green per state, ADR 0033).
- *Looks like Unity*: not proven. Against Unity's renders (ADR 0048) no export is green; most rest states are red.
  The remaining causes are not itemised and had no open issue.
- *Cheaper than the baselines*: not measured. The Unity baseline #38 was moved to Phase 1 when M0.10 closed. Our
  own before/after cost of the full exports (animators, PhysBones, contacts) had not been measured either.
- The scoring scripts lived only in the gitignored `corpus/local/`, so the evidence couldn't be regenerated from
  the repository.

Options:

1. Declare the gate passed on the evidence we have. Rejected: it is the question Phase 0 exists to answer (§21),
   and half of it was never measured.
2. Start Phase 1 and treat the gate as background work. Rejected: Phase 1's gate (40 converted avatars at 90 Hz,
   friends meeting with converted avatars) assumes the answer, and engine work would crowd it out again.
3. Reopen Phase 0 with only the gate's evidence, and start Phase 1 when it is in.

## Decision

Option 3. Milestone **M0.11 Phase 0 gate** holds the two missing proofs and is worked before epic #39 is split:

- #38: Unity CPU baselines (unoptimised, with AvatarOptimizer) next to our numbers, per export.
- #101: compiled avatars within a measured threshold of Unity's renders, with thresholds for a Unity reference
  decided from data (ADR 0033's were set for our renderer against itself).

The evidence is regenerated by one committed command, `python corpus/scorecard.py`: per Unity export, draws,
shapes, CPU and GPU µs per avatar before and after compiling, and the compiled package's FLIP against Unity's
renders. Its numbers go in the health check report and on the M0.11 issues.

## Consequences

- Phase 1 starts later. Work that both phases need (#60 MSAA if parity needs it, the measurement tooling) may run
  under M0.11.
- If #38 shows the compiled avatars are not clearly cheaper, or #101 shows parity can't be reached, that is a
  design doc question for the owner before Phase 1, not something to work around in Phase 1.
- Closing M0.11 needs a follow-up ADR that states the gate's result with the scorecard and baseline tables.
